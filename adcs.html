PKI and X.509 -- how certificates work in Windows
> what is PKI
Public Key Infrastructure is a system for issuing, distributing, and verifying digital certificates. A certificate binds a public key to an identity. A trusted third party (the Certificate Authority) signs the certificate, vouching that the key belongs to that identity. Anyone who trusts the CA can verify the certificate without contacting the CA again. The chain of trust runs: Root CA → (optional Subordinate CA) → End Entity certificate.
> what is X.509
X.509 is the standard format for public key certificates, defined in RFC 5280. Every TLS cert, code-signing cert, and AD authentication cert is X.509v3. The important fields: 
Subject        -- who this cert is for (DN: CN=user, OU=, DC=)
Issuer         -- who signed it (the CA)
Serial Number  -- unique ID from the CA
Validity       -- Not Before / Not After
Public Key     -- the subject's public key
SAN            -- Subject Alternative Name: additional identities
                  (UPN, DNS name, email) this cert is valid for
Key Usage      -- what the key can do (signing, encryption)
EKU            -- Extended Key Usage: what the cert is for
                  (Client Auth, Server Auth, Code Signing)
Signature      -- the CA's signature over all the above
> how AD CS implements PKI in Windows
Active Directory Certificate Services is Microsoft's enterprise PKI. It runs as a Windows Server role. The key components: 
Certificate Authority (CA)
  Signs and issues certificates. Enterprise CAs are
  integrated with AD and issue certs based on templates.
  Standalone CAs are not AD-integrated.

Certificate Templates
  AD objects (pKICertificateTemplate) stored in
  CN=Certificate Templates,CN=Public Key Services,
  CN=Services,CN=Configuration. They define what a cert
  can do: EKUs, key usage, who can enroll, whether the
  requester supplies the subject name, validity period.
  The CA reads the template at enrollment time.

NTAuthCertificates
  An AD object that lists which CAs are trusted for
  AD authentication. A cert is only valid for domain
  logon if its issuing CA is in NTAuthCertificates.

Certificate Enrollment
  Users/computers request certs via:
  - RPC/DCOM (certreq, autoenrollment)
  - HTTP (certsrv web enrollment, CES/CEP)
  The CA checks the template, validates the request,
  signs the cert, and returns it.

PKINIT (RFC 4556)
  Kerberos extension. A user authenticates to the KDC
  with a certificate instead of a password. The KDC
  validates the cert, checks the SAN for the UPN, verifies
  the issuing CA is in NTAuthCertificates, and issues a TGT.
  This is how a stolen or forged cert becomes domain access.
> why AD CS is an attack surface
Certificates are long-lived credentials (default 1 year). They survive password resets. If you can get a cert as a DA, you have persistent DA access for the cert's lifetime. AD CS misconfigurations let you request certs as other users (ESC1-3, ESC6), modify templates or PKI objects to create that condition (ESC4-5, ESC7), or relay authentication to get machine certs (ESC8). The ESC classification comes from SpecterOps' "Certified Pre-Owned" research by Will Schroeder and Lee Christensen (2021).
